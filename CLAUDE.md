## Project
This is Offhand — a privacy-first Android app that records voice notes and meetings and turns them into structured notes entirely on device.
See .claude/PROJECT_SPEC.md for full project overview, tech stack, and architecture.
POC decisions and roadmap: .claude/POC/ (read before implementing features).

## Behavior
- If you know a better solution (different API, library, pattern) — suggest it BEFORE implementing. Don't silently use a suboptimal approach.
- After every code change, run `./gradlew assembleDebug` and fix errors before finishing.
- When adding new files, auto `git add` them (only files related to current task).

- Telemetry: `FirebaseInitProvider` is removed in `AndroidManifest.xml`, so Firebase never self-initialises — `TelemetryController` initialises it (Crashlytics + Analytics) from the stored consent and switches collection off when consent is withdrawn. Since 2026-11-18 (owner decision) only new installs in the EU are asked, Apple-style, as the first onboarding step (board 25, see "Onboarding"); everywhere else sharing is on by default from the first launch, as it was since 2026-10-02. The region is `DeviceRegion.countryCode()` (core:common; Android `Locale.getDefault().country`, iOS `NSLocale.currentLocale.countryCode`, bound in `appModule` and the iOS `platformDepsModule`), and `DeviceRegion.asksBeforeCollecting` is true for the 27 EU countries and for a phone that reports no region (EU only is the owner's decision of 2026-11-18: the United Kingdom, Switzerland, Norway, Iceland and Liechtenstein are not asked). It is the device's region setting, not its location, and it is read again on every start, never stored. Consent is tri-state: `UserPreferences.telemetryConsent` is a `TelemetryConsent` (UNANSWERED / SHARED / DECLINED, `isShared`, `isAnswered`), read by `DataStoreUserPreferencesRepository` from the `telemetry_consent` key: true is SHARED, false DECLINED, and no stored value is SHARED on an install that finished onboarding (installs onboarded under the opt-out default keep sharing unless they switched it off, and are never asked, in the EU too: owner decision) outside the EU, and UNANSWERED otherwise, so an EU install that started but never finished onboarding under the old default is asked like a new one (one that answered the old consent page before it left onboarding keeps that answer and skips the question). Both `TelemetryController`s and the Settings switch ("Share anonymous usage" in Settings › Privacy, `SettingsViewModel.onTelemetryChanged`) read `isShared`, so nothing initialises Firebase (Crashlytics or Analytics) while the question is open. The smoke fakes bind a `DeviceRegion` of "DE" so the Maestro flows keep walking the question on any emulator; the device suite uses the phone's real region and `00-setup` answers the question only when it shows. `ConsentGatedAnalyticsTracker` holds events tracked while the answer is not known (UNANSWERED, or the preferences still loading at process start; at most 64, oldest dropped) and sends them only once the answer is SHARED; DECLINED drops them, and sending follows the answer at track time after that. History: consent defaulted to on from 2026-10-02 to 2026-11-17 (the owner chose opt-out after the July–September export showed 178 consenting installs and 29 completed onboardings), and before that onboarding had an opt-in consent page. Keep `ReleaseLogTree` resolving Crashlytics per log rather than capturing it, since Firebase may not exist yet when the tree is planted (a build without the config file). iOS holds the same line.

Since 2026-11-15 the build runs on AGP 9's defaults, without the `android.builtInKotlin=false` / `android.newDsl=false` opt-outs (do not bring them back, AGP 10 removes them): the plain Android modules (`app`, `core:ai-local`, `core:designsystem`, `core:ui`) use AGP's built-in Kotlin, so build-logic no longer applies `org.jetbrains.kotlin.android` and sets the JVM target on the `kotlin` extension AGP provides, and every KMP module is `com.android.kotlin.multiplatform.library` configured in `kotlin { android { } }` (`KmpLibraryConventionPlugin`: compileSdk, minSdk, JVM target, `withHostTest`; each module sets only its `namespace` there). What that plugin changes: one Android variant with no build types and no BuildConfig; JVM tests live in `src/androidHostTest` and run as `testAndroidHostTest`; Android resources are off unless `androidResources { enable = true }` (`KmpFeatureConventionPlugin` switches it on, so a core KMP module that gains a `res` folder has to enable it too); there is no `debugImplementation`, so Compose tooling sits on `androidRuntimeClasspath` and stays out of the published runtime; lint report tasks only exist because the convention plugin also applies `com.android.lint` (`lintAndroidMain`); a KMP module compiles against the debug variant of the plain Android libraries it depends on (`localDependencySelection`, debug first), because the default picks release and a debug build would compile `core:ui` and `core:designsystem` twice. AGP uses minSdk as lint's target SDK for a KMP module and ignores `lint.targetSdk` there, so the plural-quantity checks in the feature modules judge `many` for Spanish and Portuguese by API 31 rules (`UnusedQuantity` where the old setup reported `MissingQuantity`); treat those two as noise. Kotlin 2.4.21 officially lists AGP up to 9.3.1 and Gradle up to 9.7; this pair is past that and was verified by build, unit tests, lint, the minified release build, the Kotlin/Native tests, the iOS build and all Maestro flows. After a Kotlin bump check `./gradlew :core:device:lintAnalyzeAndroidMain --rerun-tasks`: "Module was compiled with an incompatible version of Kotlin" means lint's embedded compiler is older and it is silently blind to Kotlin code (AGP 8.13 was, with Kotlin 2.4). A library built with a newer Kotlin than ours fails first on Kotlin/Native ("incompatible ABI version" klibs), as kotlinx-serialization 1.13 and DataStore 1.3 did under 2.3.21, and Compose 1.12, core-ktx 1.19, lifecycle 2.11, navigation 2.10, adaptive 1.3 and OkHttp 5.5 fail `checkAarMetadata` below compileSdk 37. LiteRT-LM is 0.19.1 on both platforms and must stay in step; sherpa-onnx's AAR (2.0.1) is pinned by SHA-256 in `core/ai-local/build.gradle.kts`, so a bump needs the new hash, and iOS still links the 1.13.4 xcframeworks because later releases ship no prebuilt iOS archive (`iosApp/Tools/fetch-frameworks.sh`).

- App lock: enforced in every configuration, dev and debug included — there is no build-time escape hatch, and the removed `DEV_UNLOCK` flag must not come back. To work without the lock, leave it off (onboarding writes `app_lock_enabled = false` since 2026-11-17) or turn it off in Settings; that is the same path a user has. `NSFaceIDUsageDescription` is mandatory: without it iOS refuses Face ID outright and `.deviceOwnerAuthentication` silently degrades to a passcode prompt, which looks like "biometrics just never fire". The lock is gated on the `app_lock_enabled` preference (onboarding writes false, Settings' "App lock" switch turns it on) — `AppLockManager` only reports lock state, it does not decide whether to lock. Re-locking on background is driven by the app layer, which can see the recording session (the managers cannot, for module layering): `OffhandApplication` observes `ProcessLifecycleOwner` and `RootView.handleBackgrounded()` observes `scenePhase`, and each calls `markLocked()` — but skips it while `SessionPhase.RECORDING`, because swapping in the lock screen tears down the record sheet and strands the live capture. So an unlock lasts one foreground session, except an active recording carries across background/foreground. `markLocked()` is a no-op while the device has no credential (`isDeviceSecure == false`) on both platforms: the stored preference can be stale (pre-opt-in installs default it to on, and removing the device PIN does not rewrite it), and a lock screen with nothing to authenticate against is a dead end. Compose `takeFocus` on window-focus regain lands on the first focusable node, which on the notes list is the search field; `Modifier.userInitiatedFocusOnly()` (core:designsystem) cancels focus entering the pane unless a touch was seen within the last second, so taps still focus and show the keyboard but returning from a screen does not. (A pointer-down flag reset on the Final pass did not work: the field's focus request runs after that reset.)
- Record sheet (since 2026-11-17 this paragraph's layout is replaced by quiet-ink board 2, both platforms: an always-dark full-height sheet with "● RECORDING" / "PAUSED", the folder name, a mono timer, "Stays on your phone", the waveform, the live transcript, a round 64 pause/resume button with its caption, a light "Save note" pill and the red "Discard recording" text under them, which opens the "Discard this recording?" dialog with "Keep recording" and "Discard" and states the length; the "Cancel" corner button is gone, the labels and descriptions the flows tap are unchanged): `RecordSheetView` mirrors Android's `RecordingBottomSheet` since 2026-10-09 (the owner found the iOS buttons unclear): waveform, timer, "Recording…" / "Paused", then a tinted pause/resume circle beside a full-width "Save note" pill with a checkmark, and a red "Discard recording" text button under it. The Maestro flows tap "Save note" on both platforms, so keep that label. Discarding is a plain "Cancel" text button in the sheet's top-right corner whose accessibility description is still "Discard recording" (that is what flow 11 taps), and it always opens the "Discard this recording?" confirmation; the red text button under the controls is gone. Keep the confirmation: a lost recording is the failure users forgive least.
- The speech engine is kept warm (2026-11-16, owner request): `SpeechWarmUp` (feature:recording, started by `PendingNotesCoordinator.start()` on both platforms) loads Whisper into memory whenever the app is in front and nothing is being recorded or processed, so the first piece of a recording is transcribed without waiting for the engine to load, and frees it when the app goes to the background (`AppForegroundState`: Android's process `onStart` / `onStop`, iOS's active notifications). It never touches the engine while a session is active or a note is processing or being transcribed, which is what keeps a recording that goes on in the background safe; the busy check is repeated under a lock right before the engine is freed. It never downloads (only with the speech model on disk) and does nothing with transcription switched off. The pipeline still frees the engine itself after a live session and after transcribing stored audio, so Whisper is not held next to Gemma while a summary is written; the warm-up loads it again once that work is done. `SpeechWarmUpTest` covers the cases.
- Live text while recording (2026-11-16, a first step the owner is testing before deciding on WhisperKit for iOS and Parakeet for Android): the recorder cuts a piece at the first pause of half a second once the piece is four seconds long, instead of after 20 to 29 seconds (`AudioChunker.LIVE_*`, shared by both recorders; a stretch without pauses is still cut at 29 s for Whisper's window), and a piece counts as speech from 500 ms of it (`MIN_CHUNK_SPEECH_MS`, was one second). The record sheet shows the end of what has been transcribed so far under the status line, three reserved lines that end in three small dots, one lit in turn, while the recording is not paused (2026-11-17, owner request: the dots show that the transcript is being worked on, and the placeholder "Your words appear here as you speak." is gone, so before the first piece only the dots show; static with reduced motion, Android `LiveTranscript.kt`, iOS `RecordSheetView.liveText`) (`RecordingSession.liveTranscript` / `isTranscribedLive`, `RecordingUiState.liveTranscript` is the last 140 characters from a word boundary); it is only there while the session transcribes live, so not without the speech model and not with transcription switched off. The engines are unchanged, so the text trails the speaker by the length of a piece plus the time Whisper needs for it. A side effect to judge in the test: the transcript gets one paragraph and one time mark per piece, so they are sentence-sized now.
- Testing the lock on the Simulator: enroll biometrics with `xcrun simctl spawn <udid> notifyutil -s com.apple.BiometricKit.enrollmentChanged 1` then `notifyutil -p com.apple.BiometricKit.enrollmentChanged`, and satisfy a prompt with `notifyutil -p com.apple.BiometricKit_Sim.pearl.match`. Note that an instantaneous synthetic tap does not flip a SwiftUI `Toggle` — drive it with a touch path that dwells ~150 ms.

## Design system (quiet ink)

## Backup format
- `:feature:backup` writes a single `.offhand` file: 4-byte magic `OFHB`, version byte, PBKDF2 iteration count, 16-byte salt, 8-byte nonce prefix, then a stream of chunks (`flag | u32 length | AES-256-GCM ciphertext`), 1 MiB of plaintext per chunk, nonce = prefix + counter, AAD = magic + counter + final flag. Inside the plaintext: length-prefixed records (manifest JSON, folders JSON, notes JSON, one raw PCM record per audio file, END). The format and both use cases live in commonMain over okio; only `BackupCrypto` is per platform (javax.crypto on Android, CryptoKit + CommonCrypto in Swift via `IosBackupCryptoBridge`). Restore merges: folders match by name (case-insensitive), a note is a duplicate when title and createdAt match, in-flight notes are never backed up. Bump `BackupFormat.VERSION` for any layout change and keep old readers. Android's `TinkEncryptedAudioStore.pcmSizeOf` must read a byte before calling `size()`: Tink's keyset-wrapped seekable channel throws until the first read, and callers wrap the call in `runCatching`, which silently turned every recording into 0 bytes and dropped audio from backups. The backup KDF on Android is the hand-rolled `Pbkdf2HmacSha256` over the raw UTF-8 passphrase bytes, because `PBKDF2WithHmacSHA256` re-encodes chars and would not match iOS's CommonCrypto for non-ASCII passphrases.

## Smart suggestions (calendar events)
- `CalendarEventExtractor` (feature:recording) runs `CalendarSuggestionPrompt` on the transcript (or the overview when the transcript does not fit the window) and parses `CalendarEventSuggestion`s. The prompt anchors on the note's recording date and spells out the next 14 days with weekdays, because Gemma E2B miscounts weekdays otherwise (it put "next Tuesday" one day after a Wednesday recording). Keep that list and the "at most three sentences" thinking rule: the answer must stay inside the output budget, and `CalendarSuggestionParser` already tolerates weekday-prefixed dates, times inside words, bare arrays and answers truncated mid-object.
- The extraction is a pipeline step, not a menu action: `RecordingSessionManager.processNote` runs it right after `completeNote` while still holding the processing lock and still counting the note as processing (so the Android foreground service outlives it and no retry can interleave); `suggestingNoteIds` tells the UI to show the spinner once the overview is already READY. Results live in the `note_suggestions` table (DB v9, one row per note, events + per-event `PENDING/ADDED/DISMISSED` status as JSON) behind `NoteSuggestionsRepository`; no row means "never run", an empty row means "no suggestions". `MarkNoteProcessingUseCase` clears the row, so re-transcribing or restyling resets the section; nothing else does, and deleting the note deletes the row. Notes from before this version and restored backups have no row and show a "Find suggestions" button, which goes through `RequestNoteSuggestionsUseCase` → `RecordingProcessController.suggestEvents` (service on Android, direct on iOS) so the same locked path persists the result. Suggestions are not part of the backup format.
- UI: a "Smart suggestions" card between Summary and Transcript on both platforms, horizontal cards with "Add to calendar" / "Added" and a dismiss cross; dismissed cards are hidden and an all-dismissed note reads as empty. Review before hand-off is non-negotiable: "Add to calendar" opens the platform's own editor with the fields prefilled. Android uses `ACTION_INSERT` on `CalendarContract.Events` with a `vnd.android.cursor.item/event` fallback and no calendar permission, marks the suggestion Added as soon as the editor opened (the insert intent reports nothing back), and a device without any calendar app (the owner's Galaxy) gets a dialog. iOS presents `EKEventEditViewController` (no authorisation needed on iOS 17+) and marks Added only on `.saved`.
- Off by default: the Settings toggle "Show smart suggestions" (`smartSuggestionsEnabled` preference) hides the section for everyone and makes the pipeline skip the extraction (recording's `IsCalendarSuggestionsAvailableUseCase` = toggle on AND Pro), so nobody pays the extra seconds unasked. Switching it on is the Pro action: `SettingsViewModel.onSmartSuggestionsChanged(true)` goes through `ProUpgradeGate.requirePro()` and the toggle stays off when the paywall is declined. With the toggle on, a free user (lapsed purchase) sees `SmartSuggestionsUi.Locked`: the crowned card with "Find suggestions", which gates before `RequestNoteSuggestionsUseCase`. ## Processing reliability (checkpoints, background resume)
- Transcription is checkpointed: `TranscriptionCheckpoint(noteId, transcribedBytes, transcriptionTimeMs)` (core:data, table `transcription_checkpoints`, DB v10, `TranscriptionCheckpointRepository`) records how much of the stored PCM has been transcribed, and the finished text already sits in the note's transcript (`persistTranscript` after every window and every live chunk). `RecordingSessionManager` saves it after every 29-second retry/import window and after every live chunk (`recordedBytes` accumulates `durationMs * BYTES_PER_MS`, which matches the backup file because the chunker feeds every non-paused frame to both), clears it when a transcription loop reaches the end of the audio, when a recording finishes normally and when a note completes. A checkpoint therefore means "transcription unfinished": `ResumeInterruptedNotesUseCase` sends such a note through `retryNote`, which skips `transcribedBytes` of the backup and continues with the note's transcript as the finished windows, and only restructures when no checkpoint exists. A failed transcription keeps its checkpoint on purpose so "Try again" continues; a user-initiated "Re-transcribe" (`NotesViewModel.onRetranscribeConfirmed`) clears it first and starts over. Deleting a note deletes its checkpoint (`RoomNotesRepository.deleteNote`).
- Interrupted, not failed (1.4.1): iOS denies the AI engines to an app that left the foreground, so a note that was processing when the user went home used to fail after the ~30 s grace period. `RecordingSessionManager` now settles every processing failure through `settleFailure`: when the app is not in the foreground, or the note's processing spanned a background stretch (`backgroundedNoteIds`, filled from `AppForegroundState`), the note becomes `NoteStatus.INTERRUPTED` and a `NoteProcessingEvent.Interrupted` is emitted instead of FAILED; a live recording whose chunks failed to transcribe is sent through the stored audio (`retryNote`) rather than structured with holes. INTERRUPTED shows a paused card with a Continue button on both platforms (`NotesViewModel.onResumeProcessingRequested` → `ResumeInterruptedNotesUseCase`, which now also picks INTERRUPTED notes up), and it resumes on its own: iOS `onReady` on every activation, Android `RootViewModel.resumeInterruptedNotesOnReturn` on every foreground return, and `PendingNotesCoordinator` the moment an Interrupted event arrives while the app is already in front (the event is emitted only after the note left `processingNoteIds`, and `claimProcessing` makes the retry check-and-add atomic, so two resumers cannot double-start a note). A second failure without a new background stint is a real FAILED. `AppForegroundState` (core:data) is `ProcessForegroundState` on Android (app module, ProcessLifecycleOwner, created at Koin start on the main thread) and `IosAppForegroundState` (shared-framework, UIApplication active notifications). INTERRUPTED is not "settled", so backups skip it like PROCESSING.
- Notifications only reach a user who is away: `RecordingService` and `ModelDownloadService` skip the ready/failed/paused notifications while `AppForegroundState` is in the foreground, and iOS `NoteNotifications` does the same (`applicationState != .active`) and presents nothing in `willPresent` while the app is active (a notification that fires during the hand-off to the background, like the keep-open reminder with its 3 s trigger, must still show, so `willPresent` checks the state instead of always answering empty; an always-empty answer silently dropped it). On iOS the moment the app backgrounds with unfinished work, `remindToKeepOpen` posts the Threads-style "Your note is still being prepared / Come back to Offhand and keep it open" reminder (identifier `note-pending`, cleared on activation), the background-task expiry reminder and the Interrupted event both read "Your note is paused / Open Offhand and it will finish.", and while anything is processing the notes list shows the `KeepOpenBanner` and the processing card the `KeepOpenHint` ("Keep Offhand open until your note is ready."). All of these texts are plain (no "iOS", "background", "transcribing" or "re-transcribe"; the owner reviewed the stack on 2026-10-01), and nothing in the stack uses a warning colour or icon: the app's Live Activity ends in `pausedBySystem` (blue pause circle, "Your note is paused / Open Offhand to finish it", 15 min) through the static `NoteFinishCoordinator.onExpired` on both the iOS 26 continued-processing path and the legacy one, and the iOS 26 system task is re-titled to the paused wording and completed with `success: true` on expiry, because the system presents `success: false` as a failed task. There is no onboarding notifications step any more (2026-10-02): both platforms ask for notifications right after the first recording is stopped (`RecordingViewModel.onStopRecording` raises `isNotificationPromptRequested` once per install, `notificationsPrompted` preference; Android's `RecordingSheetHost` owns the `POST_NOTIFICATIONS` launcher because the sheet closes on stop, iOS reads `isNotificationPromptPending` synchronously in the stop button and asks through `NoteNotifications.requestPermissionIfUndetermined`), and report `notification_permission` only when a real prompt was shown. Android no longer bundles the notification permission with the microphone one.
- Nothing under a second is saved (1.5.1, 2026-10-09): `RecordingLimits.MIN_DURATION_MS` (feature:recording) is checked against the recorder's elapsed time when a session ends; a shorter recording, or a capture that failed before that much audio arrived (a headset that just dropped off, a microphone that refused to start), discards the placeholder note and its audio instead of leaving a one-second or failed note behind. The failed sheet still shows the reason. On iOS `MicAudioSource` builds a fresh `AVAudioEngine` on every open (`replaceEngine`, re-registering the configuration-change observer on it), because the input node keeps the hardware format it first saw: after a headset left, the old engine kept asking for the headset's 44.1 kHz on the 48 kHz built-in microphone and failed with `kAudioUnitErr_FormatNotSupported` (-10868) on every start until the app was relaunched, which is what the 1.4.1 "one-second empty note after removing headphones" bug was. The open is also retried the way a route change is (10 attempts over 2 s, session deactivated between attempts) for the moment the old input is still being torn down, and a route change with reason `oldDeviceUnavailable` reopens the capture even when the engine still reports itself as running.
- "Re-transcribe" in the note's three-dots menu is developer-only (`NotesUiState.isRetranscribeAvailable` from `BuildInfo.isDeveloperBuild`, both platforms); the "Try again" / "Re-transcribe" button on the failed card stays for everyone because it is the recovery path.
- iOS on-device AI download: `IosFileDownloader` uses one background `NSURLSession` (identifier `com.dmytrosamoilov.offhand.on-device-ai`, destination path carried in `taskDescription`, one serial delegate queue, reattaches to a task already running for the same URL), so the 2.6 GB download survives a suspend and a system relaunch; `AppDelegate.handleEventsForBackgroundURLSession` hands the completion to `SharedGraph.handleBackgroundDownloadEvents`. `IosRootViewModel.onReady()` restarts a missing download on every return to the foreground (`IosModelDownloadController.start()` is guarded by its running job), and `AiCoreDownloadActivityController` (RootView) mirrors `AiCoreDownloadStatus` into a Live Activity (`AiCoreDownloadActivityAttributes`, stale after five minutes because progress only flows while the app runs).
- Locked-device database access (2026-11-18, TestFlight crash on build 1.5.1 (30)): the notes database is "complete unless open" on iOS, so a connection that is already open keeps working after the device locks but a new one fails until it is unlocked, and Room opens reader connections lazily. A Room flow re-queried in the background on a locked iPhone (after the pipeline saved a note) threw `SQLiteException` from `NativeSQLiteDriver.open` into an uncaught coroutine on the main thread, which aborts the app on Kotlin/Native. Every Room `observe…` flow now ends in `retryWhileUnreadable(protectedData)` (core:data `UnreadableDatabaseRetry.kt`): a failed read waits until `ProtectedDataState.isAvailable` and runs again with a growing pause (0.5 s doubling to 30 s), so no collector sees the error. `ProtectedDataState` is `IosProtectedDataState` on iOS (shared-framework, `UIApplicationProtectedDataWillBecomeUnavailable` / `DidBecomeAvailable`, created at Koin start like `IosAppForegroundState`) and `AlwaysAvailableProtectedData` on Android. Background work that opens the database or the recordings waits for it first: `ResumeInterruptedNotesUseCase` (and with it every resume trigger) and `NoteWaveformFiller` before each measurement; `PendingNotesCoordinator` logs a resume that still fails instead of letting it escape, and the next return to the app resumes the notes. The protection class is unchanged on purpose (owner decision).
- iOS background, three fixes of 2026-11-16 (reasoned from the code and Apple's rules, to be confirmed on a device, the simulator ignores background limits). (1) The continued-processing task reports progress on a timer: `NoteFinishCoordinator.drive` reads `processingNoteIds` and `noteProgress` every two seconds and feeds `TaskProgress`, which follows the note's percent and creeps one small unit per reading (up to nine percent, about half an hour) while the percent stands still. Progress is how the system knows the task is alive, and before this it only changed when the set of processing notes changed, so one long note looked stalled. (2) The summary never runs on the GPU in the background: `IosModelManager.shouldUseGpu` is the selected backend AND `AppForegroundState`, `awaitReadyEngine` swaps a GPU engine for a CPU one before it is used while the app is away (and back once it is in front), and `IosAiBackend` retries a generation once on the CPU when it failed on a GPU engine after the app left (`reloadForBackground`). Background GPU access exists in iOS 26 but, by Apple's forum answers, only on iPads with an M3 or later, so no entitlement was added. CPU is the default backend on iOS anyway. (3) Processing that starts while the app is already in the background (a recording stopped from the lock screen) cannot get a continued-processing task, the system grants those from the foreground only; `processingStarted` now gives it the classic background task (about 30 seconds) and schedules the resume, where it used to get nothing.
- The keep-open reminder is only for work nothing is carrying (2026-11-16, after the owner's iPad test, where it arrived seconds after leaving the app while the system task was still working): `RootView.handleBackgrounded` skips `remindToKeepOpen` while `NoteFinishCoordinator.isContinuingInBackground` (a continued-processing task's handler is really running, counted in `drive`), and a task that starts clears a reminder that was already scheduled. iOS 17/18, a task the system never started and work that began in the background still get the reminder, and a task the system cuts short still posts "Your note is paused" from its expiration handler, so nobody is left waiting without being told. The task API is the same on iPhone and iPad; only background GPU access is iPad-only, and we do not use it.
- iOS background: while recording the `audio` background mode keeps the process alive. Finishing a note on iOS 26+ uses `BGContinuedProcessingTask` (one per note, `<bundle id>.finish.note-<id>`, progress from `noteProgress`); iOS 17/18 fall back to `beginBackgroundTask`. On top of both, `NoteFinishCoordinator` submits a `BGProcessingTask` (`<bundle id>.finish.resume`, registered in `OffhandApp.init` because BGTaskScheduler requires registration before launch finishes) whenever the app backgrounds with pending work or a task expires, and cancels it when all processing finishes; the handler runs `SharedGraph.resumeInterruptedNotes()` and waits for `processingNoteIds` to empty. It bails out and reschedules when `isProtectedDataAvailable` is false, because the database and audio use complete-unless-open protection and are unreadable on a locked device. None of this survives a user force quit: iOS never relaunches a force-quit app for background tasks, so the resume on next launch (`IosRootViewModel.onReady`, `RootViewModel` on Android) is the last line. Android needs nothing extra: the foreground service survives a swipe from recents and its intents are redelivered after a system kill. Android 15 caps the mediaProcessing foreground type at six hours a day: `RecordingService.onTimeout` stops the service when the budget runs out and the private `startForeground` catches `ForegroundServiceStartNotAllowedException` (the budget, or a start from the background) and stops the service instead of crashing (1.4.1 crash 3ccaabd8, fixed 2026-10-08); the work lives on the session scope and carries on while the app is open.

The open-the-app path on Android, and the Android provider is registered with the launcher. ## Architecture (summary)
- Three layers: domain/ → data/ → presentation/
- Use cases wrap repository calls. When adding a new use case, refactor all direct repo calls to use it.
- ViewModels expose UI state via StateFlow. No LiveData.
- Each screen: single UiState data class (content only — no isLoading/error, BaseViewModel handles those).
- UiState uses UI-specific models, not domain entities. Use mappers.
- All screens wrapped with BaseComposeScreen. All ViewModels extend BaseViewModel.
- Full architecture rules: .claude/PROJECT_SPEC.md#architecture

## Security (MANDATORY)
Every solution you implement MUST be secure by default. Before finishing any change, mentally walk through this checklist against the code you wrote. If a rule conflicts with convenience, the rule wins — raise the concern, do not silently weaken security.

### Secrets & sensitive data
- NEVER hardcode API keys, tokens, passwords, signing keys, URLs of private endpoints, or any secret in source, `BuildConfig`, `strings.xml`, or comments. Load from `local.properties` (gitignored) → `BuildConfig` at build time, or from a secure backend.
- NEVER commit `.env`, `google-services.json` for prod, keystores, or `local.properties`. Verify `.gitignore` covers them before `git add`.
- NEVER log tokens, passwords, PII, full request/response bodies, auth headers, or device identifiers. `Timber`/`Log` in release builds must be stripped via ProGuard/R8 or guarded by `BuildConfig.DEBUG`.
- Passwords and tokens in memory: prefer `CharArray`/`ByteArray` over `String` and zero them after use. `String` is immutable and sits in the heap until GC.
- Sensitive data in `SharedPreferences` → use `EncryptedSharedPreferences` (Jetpack Security) or `DataStore` with encryption. Plaintext `SharedPreferences` is forbidden for anything sensitive.
- Tokens on disk → Android Keystore-backed keys only. Never store private keys in files or prefs.
- Do not put sensitive data in `Intent` extras that cross app boundaries, clipboard, notifications, or URL query strings.
- Screenshots and screen recording are allowed on both platforms (owner decision 2026-09-14): no `FLAG_SECURE` on Android and no capture reaction or app-switcher cover on iOS (the former `PrivacyShield` is gone). Do not bring the blocking back.

### Networking
- HTTPS only. `android:usesCleartextTraffic="false"` and a restrictive `network_security_config.xml`. Never add a custom `TrustManager`/`HostnameVerifier` that accepts all certs — if SSL fails, fix the cert, don't bypass.
- Pin certificates for production APIs where feasible (OkHttp `CertificatePinner`).
- `OkHttp` logging interceptor: `Level.BODY` only in debug. Auth headers must be redacted via `redactHeader(...)`.
- Validate every server response before use. Never `!!` on network data. Treat all remote input as untrusted.
- Use Retrofit/Ktor with KotlinX Serialization (already in stack) — avoid reflection-based parsers on untrusted input.

### Input validation & injection
- Room: use `@Query` with parameterized arguments. NEVER build SQL via string concatenation or `SimpleSQLiteQuery` with interpolated input.
- Deep links / `Intent` extras / `Uri` params: validate scheme, host, path, and every parameter. Reject unknown. Sanitize before use in file paths, WebViews, or queries.
- File operations from external sources: canonicalize paths (`File.canonicalPath`) and verify they are inside an allowed directory to prevent path traversal (Zip-Slip, arbitrary write).
- Never pass untrusted input to `Runtime.exec`, `ProcessBuilder`, reflection, or dynamic class loading.

### Android components & IPC
- `AndroidManifest.xml`: `android:allowBackup="false"`, `android:debuggable` never set true manually, `android:exported` explicit on every activity/service/receiver/provider. Default to `exported="false"` unless there is a documented reason otherwise.
- Exported components must validate calling package/permission and sanitize all incoming `Intent` data.
- `ContentProvider`: enforce permissions, never return data for arbitrary URIs, use selection args (no string concat).
- `PendingIntent`: always use `FLAG_IMMUTABLE` (required on API 31+) unless mutability is essential and justified.
- Request the minimum set of runtime permissions. Do not add permissions speculatively.

### WebView
- Avoid WebView entirely if the task does not require it. If required:
  - `setJavaScriptEnabled(true)` only when necessary.
  - `setAllowFileAccess(false)`, `setAllowContentAccess(false)`, `setAllowFileAccessFromFileURLs(false)`, `setAllowUniversalAccessFromFileURLs(false)`.
  - `addJavascriptInterface` only with `@JavascriptInterface`-annotated methods, only for trusted origins, never exposing sensitive APIs.
  - Load only HTTPS URLs from an allowlist. Never load arbitrary URLs from intents.

### Cryptography
- Use `androidx.security.crypto` or `javax.crypto` with vetted parameters: AES-256-GCM (never ECB, never CBC without HMAC), RSA-OAEP, HMAC-SHA-256+. MD5 and SHA-1 are forbidden for security purposes.
- Keys → Android Keystore. Never hardcoded, never derived from constants, never checked in.
- Randomness for security → `SecureRandom`. Never `Random`, `Math.random()`, or `ThreadLocalRandom`.
- IV/nonce: unique per encryption, never reused with the same key, never hardcoded.
- Don't roll your own crypto. If unsure, ask before implementing.

### Authentication & sessions
- Use Android's `BiometricPrompt` via the AndroidX library, with `CryptoObject` when unlocking Keystore-backed keys.
- Session tokens: short-lived access + rotating refresh, stored in Keystore-wrapped storage. Clear on logout.
- Do not implement custom SSO/OAuth flows from scratch — use AppAuth or the provider SDK.

### Memory leaks (Android-specific, mandatory review)
Every change involving `Context`, coroutines, Compose, listeners, or long-lived objects must pass this check:
- **ViewModel** never holds `Activity`, `View`, `Context` (except `applicationContext` via Hilt/Koin), `NavController`, or any composable lambda. Breaking this rule leaks the Activity across rotation.
- **Coroutines**: use `viewModelScope` (ViewModel) or `lifecycleScope`/`repeatOnLifecycle` (UI). NEVER `GlobalScope`. NEVER `runBlocking` on main. Cancel custom `Job`s in `onCleared`/`onDispose`.
- **Flow collection** in Compose: `collectAsStateWithLifecycle()`, not `collectAsState()`, to stop collection when the screen is not visible.
- **Compose side effects**: `LaunchedEffect` keys must reflect real dependencies. `DisposableEffect` MUST clean up every listener/callback it registers in `onDispose`. `rememberUpdatedState` for captured values in long-lived effects.
- **Listeners, observers, callbacks, broadcast receivers, sensor/location listeners, `BroadcastReceiver`, `ContentObserver`**: always paired registration/unregistration tied to lifecycle. Never register in `onCreate` and unregister in `onDestroy` for things that should be `onStart`/`onStop`.
- **Static fields**: never hold `Context`, `View`, `Activity`, `Fragment`, or anything that transitively references them. Singletons only take `applicationContext`.
- **Inner classes / anonymous classes** inside Activity/Fragment that outlive the host → use `static` equivalent (top-level class or object) with `WeakReference` to the host.
- **Bitmaps, `Cursor`, `InputStream`, `FileChannel`, `MediaPlayer`, `Camera`, `Sensor`**: always `use { }` or `try/finally close()`. Never rely on GC.
- **Compose**: do not capture `Activity`/`Context` inside `remember { }`. Use `LocalContext.current` at read time, not stored.
- Run LeakCanary in debug builds; if adding a new long-lived holder, consider whether it is leak-prone and document ownership.

### Build & ship
- Release builds: `minifyEnabled true`, `shrinkResources true`, ProGuard/R8 rules that strip `Log` and keep crash-reporting line info.
- `debuggable false`, `allowBackup false`, `usesCleartextTraffic false` in release.
- Strip unused permissions, unused exported components, unused dependencies.
- Run `./gradlew lintAndroidMain lintDebug :app:lintDevDebug` — treat security lint warnings as errors.

### LLM-specific anti-patterns to actively avoid
These are mistakes AI assistants (including me) repeatedly make. Treat them as forbidden:
1. Bypassing an SSL error by trusting all certificates "to make it work."
2. Using `GlobalScope.launch` because it compiles without a scope parameter.
3. Catching `Exception` and swallowing it to silence a crash.
4. Storing a token in plaintext `SharedPreferences` "for now."
5. Putting an API key in `BuildConfig` read from a checked-in gradle constant.
6. `exported="true"` left as default on new components.
7. Forgetting `FLAG_IMMUTABLE` on `PendingIntent`.
8. Using `String` to hold a password.
9. Building a SQL `WHERE` clause via `"... = '$input'"`.
10. Passing `this@Activity` into a ViewModel constructor or repository.
11. `collectAsState()` instead of `collectAsStateWithLifecycle()`.
12. Logging the full HTTP request/response in a debug interceptor without redacting auth headers.
13. `setJavaScriptEnabled(true)` + `addJavascriptInterface` + URL from an `Intent` extra.
14. Using `Random` for a token, session ID, or nonce.
15. Adding `READ_EXTERNAL_STORAGE`/`MANAGE_EXTERNAL_STORAGE` when Scoped Storage / SAF / `MediaStore` would work.
16. Parsing a deep link `Uri` and passing parameters straight into a repository or `WebView.loadUrl`.
17. Registering a listener in a composable without a matching `DisposableEffect { onDispose { ... } }`.

If you are about to do any of the above, STOP, flag it, and propose the secure alternative before writing the code.
